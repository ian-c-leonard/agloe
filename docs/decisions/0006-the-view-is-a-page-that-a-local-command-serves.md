# 0006. The view is a page that a local command serves

- **Status:** Accepted
- **Date:** 2026-11-20
- **Decided by:** Ian Leonard

## Context

The COMPILER's report is made for an agent that plans a TRIP. A person needs to see the same TRIP: who is where and when, what is decided, what is still open, and what the report says. A person and their agent work on one FILE, so what the person sees has to follow the FILE as the agent changes it. Whatever it says about whether a TRIP works has to be Agloe's own answer.

The COMPILER answers a weekend for four PERSONs in about a second where the TRIP works. Its solver has no build for browsers. The reference checker runs in a browser, and it is too slow for a weekend.

## Options considered

1. **A page that runs the reference checker in the browser,** as the home page does. Only small TRIPs get an answer.
2. **A service on the internet that runs the COMPILER.** Anyone with a browser can use it. It needs a host to run and to protect, and the FILE leaves the person's machine.
3. **A page that a command serves on the person's own machine.** The COMPILER runs beside the FILE. It works for whoever has Agloe installed.

## Decision

The view is a page that the command `agloe view FILE` serves on the person's own machine.

- The command watches the FILE. A state of the FILE is its content at one look, and each new state gets a number, its revision. For each state the command tells the page that there is a FILE to check, and runs the COMPILER on that content in a process of its own. It sends the TRIP as a page draws it as soon as the FILE is read, the answer as soon as it is proved, and then the report in words and as JSON. A check that is still running when the FILE changes again is ended.
- Nothing in the view judges a TRIP. Every mark on the page comes from the FILE or from the COMPILER's report on that FILE.
- The command reads the FILE for the page, with the reader that the COMPILER uses. It sends what a drawing needs: the names, the days, who takes part in each step, and each time on the clocks that the report shows times on. It sends this twice for each state of the FILE. The first time is as soon as the FILE is read, from the FILE alone: a report can take minutes, and what the FILE holds needs none. The steps are then the OPTIONs that a LOCK names, and the page says that it has no report on the FILE yet. The second time is with the report, and then the page draws the plan and marks what the report names. Each name is as the report shows it: with its id where another of its kind has the same name, and in quotes where it could be taken for something else. Two names that a page shows alike come with their ids too. The page itself reads no FILE, and works out no time.
- Everything that the page is sent names the revision it is about. The page shows no answer on a state of the FILE until the COMPILER has answered on that state. While a check runs, the page marks what it still shows of the report on the FILE as it was before. Once the FILE as it is now is read, the page draws that FILE. A report that is still on the page is then marked as the one on the FILE as it was, and its lines are tied to nothing that the page draws. The page always draws the newest TRIP that it was sent. It marks that drawing too where it is not of the FILE as it is now: after a change, until the FILE is read again, and for as long as the FILE cannot be read. When the page no longer hears the command, it marks all that it shows, and says that this is the last it was sent. It speaks of a change to the FILE only where the command had said that there is a newer state. It repeats what it said last, as the last that it said: an answer that was proved, or why there is no report. When the command speaks again of the state that the page knows, all that the page was told of that state stands.
- A FILE with no report gets the reason instead. The page shows the problems that the format names, or says that the FILE cannot be read, or that a check stopped before its report came. It says each of these in its own words, and never as an answer.
- The command serves the person's own machine only, and the page asks no other host for anything.
- The view lives in [`src/agloe/view/`](../../src/agloe/view/), so it is installed with Agloe: the program that serves, and the page as files beside it. The page is plain HTML, CSS and JavaScript, with nothing to build.
- The view has its own part of the [roadmap](../ROADMAP.md). It is built alongside the releases and does not delay them.

## Consequences

- A person needs Agloe on their machine to use the view. The view is checked on Linux and on macOS, as the rest of Agloe is. A view for people without it needs the first or the second option, by a decision of its own.
- The view shows what a report holds. A report shows an ITINERARY that the travelers can use only for a FEASIBLE TRIP.
- The page draws a calendar of the TRIP: a column for each day, and in it a column for each PERSON. The days run from the first step, or from when the TRIP starts, to the last step, or to when the TRIP ends. For a FEASIBLE TRIP the calendar holds the ITINERARY of the report, and it marks each PERSON whom no LOCK names for an OPTION. For any other TRIP it holds only the OPTIONs that a LOCK names, at the times the FILE states, and it says so. OPTIONs that one PERSON is in at the same time stand side by side.
- The calendar marks what a report names. Each step that the view sends names the FACTs and DECISIONs of the FILE that are about it. A report on a TRIP that cannot work names the FACTs, WANTs and DECISIONs that rule out every plan. So a red edge is on each step that those are about, and on the start or the end of the TRIP. A report on a TRIP that depends on what the FILE does not say names, for each case in which the trip works, what that case needs. So a yellow edge is on each step whose OPTION a case names, with the report's own words for the case. The page judges nothing: it finds the same ids in both.
- The page ties each line of the report in words to the step that it shows, or to the record that it names. A report shows a plan one step to a line, puts what it warns of under the step, and starts the line of a record with its id. It states each case in which a trip works in a sentence, or on a numbered line. So pointing at a step lights up what the report says of it, and pointing at a line lights up what it is about. Pointing at a drawing lights up every drawing of the same step, PERSON, PLACE, OPTION, WAY, WANT, CAPABILITY or OBJECT, and no drawing of another, though one line of the report may be about both. The calendar puts a yellow edge on each step at which the report warns of something, with the report's own words. This is in [`src/agloe/view/static/lines.js`](../../src/agloe/view/static/lines.js), which a test runs on every example.
- Above the calendar, a strip shows all the days of the calendar at once: a row for each PERSON, and time from left to right. The strip is the calendar on its side. [`src/agloe/view/static/strip.js`](../../src/agloe/view/static/strip.js) takes the calendar as it is laid out and puts its days one after another in the pixels that the page has, so the strip holds the same marks with the same edges, and no others. Where the calendar does not show some hours between two days, the strip leaves them out, and it says so. A strip is narrow: steps that are too close together to show apart at its width are one mark, which says how many they are and names each. Pointing at a step on the strip lights up the same step in the calendar and in the report, and a click brings it into view in the calendar. A calendar that shows one day has no strip.
- The page shows every PERSON of the FILE: where a FACT says they start from, or that the FILE does not say, and where a WANT has them end the TRIP. Each row has the colour of the PERSON's column in the calendar. The name over that column and the name beside the PERSON's row of the strip are drawings of the PERSON too, so pointing at one of the three lights up the others. This is in [`src/agloe/view/static/persons.js`](../../src/agloe/view/static/persons.js). A PERSON has the red edge where the report names the FACT about where they start from, and the yellow edge where the report names them in what the FILE does not say. Pointing ties the row to the report.
- The page shows the WANTs of the FILE: for whom each is a must or a must-not, and under it each OPTION that a FACT says SATISFIES it or does not, with its DEGREE OF SATISFACTION. Beside each of those OPTIONs it says who takes part in it in the plan of the report, or whom a LOCK names for it where the report shows no plan. It has the red and the yellow edge where the report names a WANT or such a FACT, and pointing ties it to the calendar and to the report. The page does not say whether an ITINERARY SATISFIES a WANT: that is for the COMPILER. This is in [`src/agloe/view/static/wants.js`](../../src/agloe/view/static/wants.js).
- The page shows every OPTION of the FILE, whether or not a LOCK names it or a plan uses it: where it is, when the FILE says it starts, how long it takes, how early people must be there, and whom a LOCK names for it. Where the FILE does not say one of these, the page says that it does not. It words a start and a length as the report does, and it names the time zone whose clocks show the times. Where the report shows a plan, the page says who takes part in the OPTION in that plan. This is in [`src/agloe/view/static/options.js`](../../src/agloe/view/static/options.js). It has the red and the yellow edge of what the report names, and pointing ties it to the calendar and to the report.
- The page shows the rights to the OPTIONs of the FILE. The row of each OPTION says whether people need a right to take part, or that the FILE does not say. Each OPTION that needs a right, or that the FILE has a right for, has a card with its BOOKINGs and its OFFERs: whom a BOOKING covers, and how many places an OFFER has and at what price. The card says whether the FILE lists every right to the OPTION. Where the report shows a plan, the page says who uses each BOOKING and who takes a place of each OFFER, as the report states it: whether everybody who takes part has a right is for the COMPILER to say. Where the plan buys a place only if the OPTION turns out to need a right, the page says so. A line of the report that says who buys a place is tied to the OFFER: the warning under a step of a plan, and the one plan that the report gives for a case in which a trip works. This is in [`src/agloe/view/static/rights.js`](../../src/agloe/view/static/rights.js). A BOOKING and an OFFER are things of their own, with the red and the yellow edge of what the report names, and pointing ties each to its lines in the report.
- The page shows the BUDGETs of the FILE: the PERSONs who may draw on each, the currencies it holds, each cap on what the TRIP spends from it, and what the BOOKINGs state that they paid from it. A BOOKING says what it paid where it stands among the rights too, and where the FILE has a cap it says so where it states no payment. The row of each PERSON names the BUDGETs that they may draw on. This is in [`src/agloe/view/static/budgets.js`](../../src/agloe/view/static/budgets.js). The page adds up no money: whether a cap holds is for the COMPILER to say. Where the report shows a plan, a cap says what the report says is charged to it and what it has left, in the report's own words. A cap is a thing of its own, with the red edge of what the report names, and a payment is a drawing of its BOOKING. Where a report states the BUDGETs of the FILE, the line of each is tied to it.
- The page shows every WAY of the FILE, whether or not a plan uses it: the PLACEs it goes between, whether a PERSON can take it in both directions, and how long it takes. Where the FILE does not say how long, the page says that it does not. Where the report shows a plan, the page says who takes the WAY in that plan, and when. Under the WAYs it shows each FACT that the FILE lists every way of some travel, in the report's words: from which PLACE, to which, and within which span of time. This is in [`src/agloe/view/static/ways.js`](../../src/agloe/view/static/ways.js). It has the red and the yellow edge of what the report names, and pointing ties a WAY to each step in which somebody takes it and to the report.
- The page shows the CAPABILITIES of the FILE: every PERSON with whether a FACT says that they have the CAPABILITY, that they do not, or nothing, and under them each OPTION that a FACT says requires it or does not. It says whether the FILE states every one of its OPTIONs that requires it. Where the report shows a plan, the page says who meets what an OPTION requires, in the report's words, and only where the report names them: whether a requirement is met is for the COMPILER to say. Each line of the report that says who meets a requirement is tied to the step that its OPTION is. This is in [`src/agloe/view/static/capabilities.js`](../../src/agloe/view/static/capabilities.js). It has the red and the yellow edge of what the report names, and pointing ties it to the calendar and to the report.
- Each part of the page that shows what the FILE holds is loaded by itself and drawn by itself. A part that fails leaves the others, the answer and the report on the page.
- The page shows the OBJECTs of the FILE: where each is when the TRIP starts, or that the FILE does not say, each OPTION that a FACT says requires it or does not, each OPTION that a FACT says refuses it or does not, and each OPTION that a FACT says hands it over, keeps it, carries it or leaves it alone. It says whether the FILE states every OPTION of each kind. This is in [`src/agloe/view/static/objects.js`](../../src/agloe/view/static/objects.js). By the rules, an OPTION that refuses an OBJECT takes it from no PERSON. So where one FACT says that an OPTION hands an OBJECT over or keeps it, and another that the OPTION refuses it, the card says what the two come to: nobody can take the OBJECT there, or nobody who has it can take part. An OPTION that carries the OBJECT and refuses it still carries it, and the card says that it does so from no PERSON. Where an OBJECT is in a plan is for the COMPILER to say. The report says it, and its lines are tied to the OBJECT: who takes it at a step, the step it is carried in, where it is from then on, and where it is just before an OPTION that requires it or refuses it starts. Where the report shows a plan, the card of the OBJECT says the same: where the OBJECT is throughout the plan, and under each OPTION that requires it or refuses it, where it is just before that OPTION starts. An OPTION of the plan of which the report says that the FILE does not say whether it requires the OBJECT, or whether it refuses it, is under the OBJECT too, with the same. The page words this as the report does, from what the report as JSON holds, and with each name as the page shows it: two names that look alike have their ids. An OPTION that an OBJECT has to be at hand for has the yellow edge where the report names it so, and so has one that an OBJECT has to be kept out of.
- The page shows every PLACE of the FILE with what the FILE puts there: the PERSONs who start from it, each OBJECT that is there when the TRIP starts, the PERSONs that a WANT has end the TRIP there, each OPTION that happens there or goes from it or to it, and each WAY that goes from it or to it. A PLACE that nothing in the FILE is at says so. This is in [`src/agloe/view/static/places.js`](../../src/agloe/view/static/places.js). A PLACE has the red edge where the report names one of the FACTs or WANTs that put something there. It has the yellow edge where the report names it in what the FILE does not say: that an OBJECT is there when the TRIP starts, or that there are other WAYs from it or to it. Pointing at a PLACE lights up the lines of those records and cases, and pointing at an OPTION or a WAY under it lights up its steps. Who is at a PLACE at a time of a plan is for the COMPILER to say: the calendar shows it.
- The page has a row of links to its parts, in the order of the page: the calendar, each part that shows what the FILE holds, and the report. A link has the heading of its part and how many things the part holds. It has the red edge or the yellow edge where something in the part has it, so a reader of a long page sees at once where the report names something. A click on a link brings its part into view, and the keyboard reaches each link. A link is pale where its part is. On a window of one column the row stays at the top while the page scrolls, and a part comes to rest under it. On a wide window the row is above the two panes. A FILE of real size makes a long page: a weekend of two days with twelve OPTIONs is nearly nine windows tall.
- The keyboard reaches what the pointer does. In each part of the page, and in the report, one drawing takes the keyboard by Tab: the one that it was on last there, or the first. The arrow keys, Home and End move from it to the others of that part. With Shift they are the browser's, which selects text with them. So a part is one stop for Tab, however many drawings it holds, and the row of links leads to each part. The strip and the calendar are a part each, and the steps under the calendar that have no time are of the calendar's part. The drawing that the keyboard is on is lit as under the pointer, with the lines of the report that it is tied to, and has a ring around it. What the reader used last, the keyboard or the pointer, says what is lit. A key makes it the keyboard, whether or not the key moves the keyboard. A key that only changes what other keys do, like Shift, does not. A move or a press of the pointer makes it the pointer. After a key, a drawing that scrolls under a pointer at rest is not pointed at. A finger on a screen points with a tap: the drawing that it taps is lit once the finger has lifted, and the keyboard is on it. A swipe points at nothing. The page never moves the keyboard by itself. Where it draws a part again, the drawings of that part are new ones. A drawing that the keyboard was on is then gone: the keyboard is on nothing, nothing is lit by it, and the next Tab goes on from where it was. The same holds for a link of the row whose part goes. The page does not guess which new drawing is the old one.
- On a wide window the page fills the window and does not scroll. Under the answer are two panes, side by side: what the page draws, and the report. Each scrolls by itself, and the keyboard reaches both, and the calendar where it is wider than its pane. The panes keep a height that a reader can use: where the window is too short for that, the whole of it scrolls. So the answer stays in view, and so does the report while the reader looks through the drawings. Pointing at a drawing brings the first of its lines in the report into view there. The report stays as it is where one of those lines is in view already, and while the pointer stays on one drawing. Only the report moves, so the drawing stays under the pointer. On a narrower window the page scrolls as a whole, and the report is below the drawings.
- The command works out which day a step is on, and which part of it lies on each day, by the time-zone database pinned with Agloe. A day on which the clocks change is two columns, one before the change and one after, and each names its offset from UTC. So two moments that the clocks show as one time of day are never drawn as one. A time gives its offset from UTC wherever the report gives its times with theirs, and it is written the same way. It also gives its offset where the times on the page are not all at one offset, and where the clocks show one of them twice: only the offset says which of the two it is.
- The answer and the report show without the calendar. A calendar that fails to load or to draw leaves both on the page. A report reaches the page whatever becomes of its calendar: where what the calendar draws cannot be made, or is not what a page can draw, the report comes without it.
- The calendar is laid out in [`src/agloe/view/static/calendar.js`](../../src/agloe/view/static/calendar.js), which has no page in it. A test runs it with Node on every example, and checks its words against the report.
- A few tests drive the page itself in a real browser, through Playwright: what the pointer lights up, where a click goes, whether the pointer can reach each mark, and what stays on the page when a part of it cannot load. Playwright is installed for development only, and nothing of it is in the package. The checks run these tests on Linux. Where no browser is installed, they are skipped.
- A check that takes long shows its answer first, and the page says that the report is on its way.
- The words the page shows for each state are worked out in [`src/agloe/view/static/state.js`](../../src/agloe/view/static/state.js), which has no page in it. A test runs it with Node on what the command sends for the examples.
- The tests start the view on an example, change the FILE, and read what a page is sent. They also stop the command while a page listens, and put a program that never ends in the place of a check.
- The view serves a port from 1024 to 65535 that browsers open. Where no port is given, it takes a free one of those. It refuses a request that names another host, or that says it comes from another site, and it tells the browser to show the page in no other page.
- Each view has a name of its own and says it with each new state of the FILE. A page that listened to one view lets its report go when another view answers at the same address.
